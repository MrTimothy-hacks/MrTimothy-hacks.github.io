A cybersecurity internship at Redynox covering two core disciplines: network security analysis and web application penetration testing. All activities were conducted in controlled, legal environments — either on personal home network infrastructure or intentionally vulnerable lab applications designed for security training. A genuine real-world vulnerability was discovered during the network analysis task.

TASK 01 Network Security Analysis

Objective: Understand network security fundamentals by researching common threats, implementing basic security measures on a home network, and capturing and analysing live network traffic with Wireshark.

1.1 Firewall Configuration

Windows Defender Firewall was accessed via wf.msc and confirmed active across all three network profiles (Domain, Private, Public) with inbound connections blocked by default. A custom inbound rule was created to explicitly block Telnet on TCP port 23 — a legacy protocol that transmits all data including credentials in plain text.

firewall rule — block telnet
# Via Windows Defender Firewall — Advanced Security (wf.msc)
Rule Type:     Inbound
Protocol:      TCP
Port:          23 (Telnet)
Action:        Block the connection
Profile:       Domain, Private, Public
Name:          Block Telnet

The home router was also hardened: WPA2 encryption enforced, default admin password changed, and default SSID updated to avoid revealing the router manufacturer.

1.2 Live Traffic Analysis with Wireshark

Wireshark was installed with the Npcap driver and configured to monitor the active Wi-Fi interface. A live capture session was initiated while browsing to generate diverse traffic. Display filters were applied to isolate specific traffic types:

wireshark — display filters applied
# DNS traffic
dns
# Result: continuous background queries to router (192.168.8.1)
# Domains: fotmob.com, x.com, fonts.gstatic.com, mozilla-ohttp.fastly-edge.com

# TLS encrypted traffic
tls
# Result: 264 encrypted packets (TLSv1.2 + TLSv1.3) — all unreadable Application Data
# Encryption confirmed working correctly for HTTPS connections

# HTTP unencrypted traffic
http
# Result: unencrypted traffic between machine and router at 192.168.8.1
# GET /login.html and GET /api.cgi?path=router&method=get_device_info — PLAINTEXT

# TCP SYN packets (outbound connections)
tcp.flags.syn == 1 && tcp.flags.ack == 0
# Result: 13 outbound connection initiations in 40 seconds
# All to known providers: Google, AWS, Fastly, IBM Cloud — no inbound scanning
Real Vulnerability Discovered — Unencrypted Router Admin Interface · High

The HTTP filter revealed the router's administrative interface communicating over unencrypted HTTP — including GET requests to /login.html and API calls to /api.cgi. Any attacker on the same network could intercept these requests with Wireshark and capture admin credentials in plain text. This was a genuine security finding on a live home network, not a simulated lab result.

Key ObservationApplications make continuous network requests in the background even without active user interaction. DNS queries alone revealed browsing patterns, installed applications, and background services — all without decrypting a single packet.
TASK 02 Web Application Security Assessment

Objective: Set up an intentionally vulnerable web application, scan it with an automated security tool, and manually exploit SQL Injection, Cross-Site Scripting (XSS), and Cross-Site Request Forgery (CSRF).

Environment: WebGoat (OWASP) running at localhost:8080, scanned by OWASP ZAP on port 8081.

2.2 Manual Exploitation — SQL Injection (Blind)

The goal was to authenticate as user "Tom" without knowing his password — simulating a real credential theft scenario. Standard login bypass payloads in the login form produced generic error responses (a deliberate design choice to prevent information leakage). Investigation revealed the vulnerability existed in the registration form instead — requiring a blind injection approach.

blind sql injection — character extraction
# Payload injected into registration username field
tom' AND substring(password,1,1)='t

# If response = "User already exists" → condition is TRUE
# Meaning: Tom's password begins with the letter 't'
# Repeat for each character position until full password extracted

# Password discovered:
thisisasecretfortomonly

# Authenticated successfully as Tom — unauthorized account access confirmed
SQL Injection — Blind · High

The application was vulnerable to blind SQL injection in the registration form. By observing different application responses to injected conditions, the full contents of another user's password field were extracted character by character. In a real engagement, this process would be automated with sqlmap to extract complete database contents within seconds.

2.3 Manual Exploitation — Stored XSS

The Stored XSS module was used to demonstrate the most dangerous form of XSS — where the malicious script is saved to the database and executes automatically in every visitor's browser when the affected page loads.

stored xss payload
# Payload injected into comment field
<script>webgoat.customjs.phoneHome()</script>

# Instead of storing as plain text, the application executed the script
# Browser network panel confirmed POST to /phone-home-xss:
phoneHome Response is 994930725 — lessonCompleted: true
Stored XSS — Confirmed Execution · High

JavaScript payload executed successfully in the browser via a stored XSS vulnerability. In a real attack, the phoneHome() function would be replaced with a cookie-stealing script that exfiltrates session tokens to an attacker-controlled server — effectively hijacking authenticated sessions without any victim interaction beyond loading the page.

2.4 CSRF — Identified via Automated Scan

CSRF was identified by OWASP ZAP, which flagged 5 instances of "Absence of Anti-CSRF Tokens" at medium severity. HTML forms — including the WebGoat login form — submitted POST requests with no token to verify the request originated from a legitimate user action.

How CSRF WorksAn attacker embeds a hidden form on a malicious website that automatically submits a request to a trusted application the victim is logged into. Because the browser automatically includes session cookies with every request, the server cannot distinguish the forged request from a legitimate one. No user interaction beyond visiting the malicious page is required.
SUMMARY Key Takeaways
Real vulnerabilities exist in everyday environmentsThe unencrypted router admin interface was not a simulated lab finding — it was a genuine vulnerability discovered on a live home network using Wireshark. Security weaknesses are not hypothetical.
Automated scanning is a starting point, not an endpointOWASP ZAP identified SQL injection but could not exploit it. Manual analysis was required to discover that the vulnerable input was the registration form, not the login form — something only an attacker who reads application responses carefully would find.
Blind injection requires patience and methodologyWhen applications suppress error messages to prevent information leakage, blind techniques extract data by observing behavioural differences in responses — a slower but equally effective approach that highlights why thorough testing of all input fields matters.
